## Blockers

- [ ] **`claude` renders as a prompt with no interface — and this is not the alt-screen blocker below, it is a hole in the strategy.** The renderer switches to raw xterm on alt-screen enter (`\x1b[?1049h`), and `syncMode` reads `buffer.active.type === "alternate"`. **Claude Code is an Ink app, and Ink does not use the alternate screen** — it renders *inline*, repainting its frame in place with cursor moves and line clears. So no alt-screen event ever fires, `mode` stays `blocks`, and the block renderer reads a buffer being overwritten dozens of times a second back out with `translateToString`, which is why a prompt appears and the interface does not. The same is true of most modern Node TUIs; `vim` and `htop` are the *easy* case, and they are the two the design was checked against. Deciding what else trips raw mode is architecture work, not a patch, and it belongs in front of Phase 7: candidates are the DEC private modes an inline TUI does set (bracketed paste `?2004h`, mouse tracking `?1000h`/`?1006h`, cursor hide `?25l` sustained), or a repaint-rate heuristic (n full-line rewrites of the same rows inside one second), or an explicit opt-out list. Each has a false-positive cost that lands on ordinary output, which is the thing that must not break. `src/routes/+page.svelte`, `syncMode`.

- [x] **Starting as administrator opened two black, unresponsive windows — feature reverted on Windows.** A launch log settled it: the relaunch logic was correct by the third attempt (one relaunch, one exit, exactly one window shown per cycle), and the app was *still* wrong. The second window was never ours — a debug build is a console-subsystem binary (`windows_subsystem = "windows"` is release-only in `main.rs`), and the elevated child cannot inherit the dev CLI's console across the UAC boundary, so Windows hands it a fresh one: black, with a caret. What could not be fixed in place is that Tauri creates the windows declared in `tauri.conf.json` *before* `setup` runs, so the config cannot be read until after the webview exists — killing the parent then left `Failed to unregister class Chrome_WidgetWin_0`, ended the `tauri dev` session (the CLI is tethered to that process), and raced the elevated child for the shared `EBWebView` data folder, which is what "sometimes does not load" was. Reverted: the setting is Unix-only (`sudo -E` around the shell, GUI unprivileged) and the switch is absent on Windows rather than disabled. Full reasoning in [decisions.md](decisions.md). Three fixes were written and thrown away on the way — an env var that ShellExecute does not carry across UAC, a graceful `app.exit()` that had no event loop to run on, and a `-WindowStyle Hidden` for the console — and all three were real bugs in a design that was wrong anyway, which is the lesson worth keeping.

- [ ] **Docked input bar and raw xterm view (`vim`/`htop`/`claude`) still broken.** **Partial root cause found, by compiler warning rather than by reading:** `atPrompt` was a plain `let`, not `$state`, while the template reads it twice — the live prompt line in the scroll stream (`{#if atPrompt}`) and the caret's idle class. Svelte 5 compiles a non-rune `let` as a constant read, so both were pinned to their initial `false` for the whole session: the live prompt line never rendered once, and the caret never left idle. The mirror logic was correct the entire time; nothing re-read it. **This is why four rounds of tuning `PS_PROMPT` changed nothing** — the regex was never the failing part. Fixed.

  Still open: whether that accounts for the whole input-bar symptom, and the alt-screen half, which this does not touch. **F3 now opens a debug overlay** (`src/routes/+page.svelte`) dumping mode, buffer type, the three prompt flags, cursor position, the JSON-quoted cursor row, whether `PS_PROMPT` matched it and what survives the strip, plus a rolling log of OSC 133 payloads, `onBufferChange` events, and — the decisive one — any `CSI ?1049h/l` seen, watched via a pass-through CSI handler. That answers "does ConPTY forward the alt-screen swap at all", which no amount of code reading can. F2 captures the overlay, so a report is two keypresses. Previously tried and still recorded for reference: (1) `PS_PROMPT` regex made the trailing space after `>` optional, since `translateToString(true)` trims trailing whitespace and an untyped prompt row ends at `>`; (2) stripped the leading `/` OSC 7 puts before a Windows drive letter (`file:///C:/Users/vadim` → `/C:/Users/vadim` → `C:/Users/vadim`); (3) alt-screen detection (`syncMode()`) now also runs from the per-chunk write callback, not only `onBufferChange`, in case the swap event doesn't fire reliably; (4) the block that launched an alt-screen app stops snapshotting once `mode` flips, since its rows live in the buffer that gets wiped on exit. User confirmed still not working after all four — root cause not found. Next to check: whether ConPTY forwards `\x1b[?1049h` at all on this Windows PowerShell setup (ConPTY is known to intercept/rewrite some alt-screen sequences), and whether `PS_PROMPT` is matching the *actual* live prompt string at all (dump `rowText()` at the point it's read, don't assume `integration.ps1`'s template is what's on screen). `src/routes/+page.svelte`.

## Fixed

- [x] **The prompt rendered twice — once in the scroll stream, once in the docked bar.** Both said the same thing, an inch apart. Not a regression: the in-stream mirror was written while `atPrompt` was a plain `let`, which Svelte 5 compiles as a constant read, so it had **never rendered once** in the app's life. Fixing that flag is what put it on screen for the first time and made the duplication visible. Cut the stream copy: the bar owns the caret, the selection and the suggestion strip, and `startHandoff` measures *its* rect, so the stream copy was carrying no behaviour — only a second reading of the same text. `tailNudge` went with it (it existed solely to re-sync the tail after that line's own height appeared), as did `.block-head.live` and `.live-text`. **One thing was genuinely lost:** the stream copy was uncapped, so a command longer than the bar's three-row cap was fully readable there and now is not. If that bites, the fix is the bar growing past three rows for the input it actually holds, not a second copy of it somewhere else. `src/routes/+page.svelte`.

- [x] **After Ctrl+C on a running process, the next input never appeared.** `PS_PROMPT` was anchored at `^`. PowerShell echoes `^C` on abort and then redraws the prompt on that same row, so the row reads `^CPS C:\x>` — the match failed, the input mirror took its "no prompt on this row" bail-out, and it never recovered for the rest of that prompt cycle. Dropping the anchor fixes it: whatever precedes the prompt is the abort's own echo and is consumed with it, and the prompt's width still falls out of what the strip removed, so `cursorCol` is unaffected. `\x03` also kills every in-flight reveal now, which ANIMATION.md already required and nothing was doing. `src/routes/+page.svelte`.

- [x] **Esc did not reliably open or close the settings panel.** It was handled inside xterm's `attachCustomKeyEventHandler`, which sits on xterm's own textarea and therefore runs only while xterm has focus — so any click inside the panel disarmed the key, which is what "sometimes" meant. Moved to a single `svelte:window` capture handler; xterm's handler keeps only the `preventDefault` so the shell still never sees Esc in block mode. `src/routes/+page.svelte`.

- [x] **The input lost focus when the settings panel closed.** xterm is the input engine and cannot be clicked to regain focus, so this looked like typing being silently dead. The exit tween already owned the unmount and is the single close path; it now refocuses in the same `onComplete`. A drop does the same. `src/routes/+page.svelte`.

- [ ] **Typing `(`, `{` or `[` landed inside the prompt and the input bar went blank.** *Fix written, awaiting confirmation on a rebuild.* The overlay showed the whole story: `last key sent` was `"{"`, `cursor row` was `"PS C:\\Users\\vadim{"` — the `> ` at the end of the prompt was gone, overwritten — and `PS_PROMPT matches` was therefore `false`, so the mirror bailed and displayed nothing while the shell had the character all along. Root cause: PSReadLine remembers where the prompt ended so it can redraw the input line in place, and it derives that from the prompt string it is handed. Escape sequences in that string are zero-width on screen but not in the string, so its geometry was wrong, and the first thing to force a full-line redraw rewrote the line at the wrong column — typing an opening bracket is exactly that trigger, since PSReadLine re-renders to match and colorize brackets. Fixed by writing everything that is not visible prompt text (`133;D`, `133;A`, OSC 7) straight to the console with `[Console]::Write` instead of returning it in the prompt string; only `133;B` stays, because it marks the point after the prompt text. If it still misbehaves, the next knob is PSReadLine's own `Set-PSReadLineOption -PromptText`, which exists to tell it the prompt's plain text. `src-tauri/resources/shell/integration.ps1`.

- [ ] **A stray `\` appeared in front of typed characters and could not be deleted.** *Fix written, awaiting confirmation on a rebuild.* Same family as the bracket bug above. `integration.ps1` terminated its OSC sequences with ST (`ESC \`) — legal, and two bytes, the second of which is a backslash. Anything that drops or consumes the ESC leaves that backslash on screen as literal text, and Backspace cannot remove it because the shell's line editor never typed it and does not know it is there. The F3 overlay is what settled it: `last key sent` was `"("` while `cursor row` already read `"PS C:\\Users\\vadim>\\("`, so the character was on screen without ever having been sent. Switched to BEL (`[char]7`) — one byte, cannot be split, accepted for OSC everywhere, and what Windows Terminal's own shell integration uses. The overlay now also logs every `onData` payload (`key "…"`), so the send sequence is visible rather than only the most recent event.

- [x] **After `clear`, typing was invisible in the input bar until Enter ran it.** `clearBlocks` called `term.clear()`, which drops the scrollback *and* rewrites the screen, promoting the cursor row to row 0. The shell is never told, so PSReadLine kept redrawing the input line at the row it still believed the prompt was on — leaving the cursor row holding bare typed text with no prompt in front of it. The input mirror finds the typed text by stripping the prompt off that row, found no prompt, and produced nothing; the keystrokes reached the shell the whole time, so Enter ran the invisible command. Replaced with `\x1b[3J` (drop saved lines), which frees the same memory and moves nothing. The mirror also now bails when the prompt strip matches nothing rather than mirroring a row the prompt is not on — without that guard the same class of desync fills the bar with prompt-width padding and parks the caret in the middle of it, which is what "the caret does not return to the start" was. `src/routes/+page.svelte`.

- [x] **A phantom empty container appeared beside every real block.** The write callback's fallback opens a block for output arriving with none open. `integration.ps1` writes `133;D` and `133;A` as one string, but a PTY read boundary has no relation to the shell's write boundary, so a chunk ending between them is routine — and when it happened the callback ran with the command's block just closed by `D` and `atPrompt` not yet set by `A`, hit the fallback, and opened an empty block the following prompt had nothing to fill. Fixed with a `betweenCommands` flag, set by `D` and cleared by `A`: output in that window is shell bookkeeping, not command output, and is dropped. Exactly the same root cause as the startup-noise bug `booted` fixed — output with nothing to attribute it to — so the two guards now sit together and read as one rule. `src/routes/+page.svelte`.

- [x] **The mirrored input read as committed text.** `.live-text` was `#f4f4f5` (the brightest value in the file) and `.input-text` inherited the bar's solid `#d4d4d8`, so a preview of xterm's cursor row looked exactly as settled as a real block's command line. Both are now `rgba(244, 244, 245, 0.45)`: readable, visibly not yet the record. `.block-command` — the same text once Enter commits it — stays at full weight, so the handoff has somewhere to land.

- [x] **`PS C:\Users\vadim>` leaked into the command echo and the live input mirror.** Input mirroring cut the typed text out of the cursor row at a remembered column (`promptCol`, captured once from `buf.cursorX` when `133;B` fired). That column goes stale two ways: a window resize between prompt-draw and typing reflows every column after it, and a PTY read chunk boundary landing between the prompt text and the `B` marker means the column was captured before the prompt had actually finished rendering at its current width. Replaced with a direct regex strip of the known literal template (`PS <path>> `, from `integration.ps1`) applied fresh to the row every time — no remembered state, nothing to go stale. Also swapped the `> cwd  command` double-space separator for `> cwd | command` throughout (block heads, docked input bar, live preview).
- [x] **Output always chased the tail on every chunk, scrolling past the command that produced it for anything longer than a screen.** Replaced the per-chunk `scrollToEnd()` with `anchorNewBlock`, a Svelte action that fires once when a block is created and scrolls its head to the top of the viewport (GSAP `ScrollToPlugin`, element target). A command's output now reads top-down from where it started instead of endlessly following the newest line; the reader scrolls manually for anything that overflows.
- [x] **Long output (e.g. `git diff`) still dragged the view to the bottom** even after the fix above. The browser's own scroll-anchoring (a built-in heuristic that adjusts `scrollTop` to "keep the view stable" as a scroll container grows) was fighting the deliberate top-anchor as the block's output streamed in below the fold. Fixed with `overflow-anchor: none` on `.scroll` — the standard fix for this class of bug in any growing scroll feed (chat apps hit the same thing).

- [x] **Two empty containers appeared between the banner and the first real prompt.** PowerShell writes startup noise (loading the injected profile, its own interactive-loop setup) before the first `133;A`/`B` prompt cycle completes — that output has no cwd yet, so it fell through the "output arrived with no block open" fallback and opened headerless, contentless blocks. Fixed with a `booted` flag, set true the first time `133;B` fires; output arriving before that is dropped instead of block-ified. Also reverted the whole-window scale-in animation added earlier this session — deferred to the typewriter reveal (Phase 5, [docs/ANIMATION.md](docs/ANIMATION.md)) instead of a separate boot effect.

- [x] **Prompt text leaked into the command field; phantom empty blocks; caret drifted; banner ran through the markdown parser.** Four related bugs from the same session. (1) `integration.ps1` writes the prompt text and the `133;B` marker as one logical unit, but a PTY read chunk boundary (8 KB) has no relation to the shell's write boundary — a read could land between them, and the input mirror would read `promptCol` before `B` had actually updated it, briefly showing the raw `"PS C:\...>"` prompt as if typed. Fixed with a `promptReady` flag, set by `B`, cleared by `A`; the input mirror and Enter handling both wait on it. (2) Pressing Enter on a blank line still opened a block — skip when `input.trim()` is empty. (3) The caret was a fixed 8px block with a `-4px` negative margin overlapping the last character; switched to `width: 1ch` so it sits on the monospace grid instead of an eyeballed offset — most of the reported "wrong position on delete" was actually bug (1)'s stale mirror, not the caret itself. (4) The banner is ASCII art, not command output — gave `Block` an `md` flag; the banner (`md: false`) skips `parse()` and renders in the accent color, everything else is unaffected.

- [x] **Command output vanished — blocks showed the command line and a result, nothing between.** OSC markers were parsed in Rust and forwarded on a second Tauri channel. Two channels have no ordering guarantee against each other, and for any command that finishes fast the whole thing — output, `133;D`, `133;A`, next prompt — arrives in one 8 KB read. The events were dispatched ahead of the bytes, so `atPrompt` was already true when the output finally landed and it was routed to the input bar and discarded. Fix: markers are parsed by xterm via `parser.registerOscHandler(133/7)`, where the handler runs mid-parse with the cursor exactly where the marker sat. `osc.rs` deleted; Rust is now a dumb pipe. Alt-screen detection moved to `buffer.onBufferChange` for the same reason. The final block snapshot also had to move into the `D` handler — by the time the write callback runs, the cursor has moved onto the next prompt row.

- [x] **Every block reported the same non-zero exit code** (`exit 128` forever, after one failing `git`). `integration.ps1` read `$LASTEXITCODE`, which PowerShell only sets for *native executables* and never clears — a cmdlet error leaves the previous native command's code in place. Fixed by reading `$?` as the first statement of `prompt` (any earlier statement clobbers it), falling back to `$LASTEXITCODE` for native failures and `1` otherwise, then resetting `$LASTEXITCODE` to `0`.

- [x] **Block view showed raw ANSI, duplicated the prompt on every keystroke, and filled with garbage on resize.** The block renderer was accumulating the decoded byte stream into a `<pre>`. That stream contains every escape sequence PSReadLine emits — it redraws the entire input line on each keypress, so one typed word produced dozens of literal `ESC[93m…ESC[?25h` copies of the prompt, and a resize replayed the whole reflow. Fix: block text is now read back out of xterm's screen buffer (`translateToString`) after each write, with an `IMarker` tracking the block's first row. xterm has already applied the escapes, so redraws collapse and reflow is handled for free. Also: blocks now open on first output rather than on OSC `133;B`, since the prompt string is emitted before `B` and events arrive on a different channel than the bytes they refer to (marker would land against a stale screen).

- [x] **DSR/cursor-query garbage leaking into block view, first prompt never appeared.** Block mode was bypassing xterm entirely and dumping raw bytes into a `<pre>`, so PowerShell/PSReadLine's `ESC[6n` cursor-position query never got answered — it stalled and the literal escape leaked through as visible text. Fix: xterm now processes every byte regardless of mode (its VT emulation answers these queries automatically via `term.onData` → `pty_write`, same path as real keystrokes); block mode additionally decodes the same stream for display. Also fixed the hidden pane collapsing to 0×0 (`display:none` → absolutely-positioned + opacity toggle) which would have thrown off PTY sizing.
- [x] **PowerShell OSC markers leaked as literal text** (`e]133;D;0e]133;A...`). Windows PowerShell 5.1 does not support the `` `e `` backtick-escape — that's PS7+ only. Fixed by building ESC explicitly via `[char]27` in `integration.ps1`. Verified: prompt renders clean.
- [x] Phase 1 manual verification — `git status`, prompt render all confirmed working in-window.

## Open questions

- [ ] **"Move down" no longer changes the reveal's rate, only where the view lands.** It used to have both halves: a distance-scaled catch-up scroll, and `revealStagger`, which shortened the typewriter's burst as the backlog grew. The typewriter is gone and `reveal.js` with it, so the reveal has one duration in both modes. Whether that reads as behind in "move down" against a genuinely fast producer has not been watched. If it does, the lever is the flood threshold, not a second pacing curve — a mode that animates differently is a mode that is a different product. (Phase 5)

- [ ] **The reveal counts rows by height ÷ line box.** It assumes a uniform line height inside one element, which is why `.block` now sets an explicit `line-height`. A list with per-item margins is off by the margins, and a future embed ([foundation/phase-9-rich-media.md](foundation/phase-9-rich-media.md)) has no line box at all — `ANIMATION.md` already says an embed holds its slot in the stagger as one unit, and that is the case this heuristic cannot express. The cost of being wrong today is an uneven cadence, never content that fails to appear (the clip is cleared unconditionally), so this is a refinement and not a bug. Revisit when embeds land, not before. Marked `ponytail:` at `rowsIn`. (Phase 5 / 9)

- [ ] **Pinned-head detection is linear in mounted blocks.** One rAF-coalesced rect compare per block head, per scroll frame. Correct and cheap at today's block counts, and wrong by the time a full day of scrollback is mounted. Scrollback virtualization (PERFORMANCE.md) is the fix — that pass should hand `syncStuck` only the blocks it kept in the DOM. Marked `ponytail:` at the call site. (Phase 7)

- [x] ~~**Which reveal wins.**~~ **Settled, twice, and the second answer deleted the first.** The split — type what is live, sweep what is final — was settled without the comparison being run, and the comparison is what undid it: on real streaming output one command looked like two different products depending on where a PTY chunk boundary landed, which is an artefact of the pipe and not a fact about the text. There is now one reveal for everything (bars over the tokens, wave under the prose), played as content arrives, and the typewriter is deleted along with `src/lib/reveal.js`. `REVEAL_MODES` is `reveal` / `instant`. The cost is in [decisions.md](decisions.md): live output is revealed but never character-split, so its prose rises as one piece instead of waving. (Phase 5)

- [ ] **The static reveal's total length has not been looked at on real output.** The wave and the first tier both start at zero, so a line is readable from the first frame; but five non-empty tiers is 0.8s before the last bar even starts. Only ever spent on text that was already final, which is the argument for it being fine. Watch it against `git --help` and a long `npm` line. Knobs, in order: `LABEL_STEP`, then whether tiers overlap rather than queue. (Phase 5)

- [x] ~~**A label's bar covers the token's whole box, however many rows it spans.**~~ Fixed: the bar is measured off a `Range` over the element's contents, one bar per `getClientRects()` rect. This was not only the wrapping case — a heading or a list item is a block, so its box ran the full container width and the bar swept over empty space beside the text. (Phase 5)

- [ ] **The character wave splits real DOM into the element the framework renders into.** Guarded three ways: it runs only on elements the pass has decided are final, the original text nodes are handed back rather than re-parsed from markup, and every early-exit path calls the teardown. The residual risk is a static-looking element that turns out to update mid-wave — the text would be written to detached nodes and then restored, so it self-heals, but it has not been seen happen. Worth a look if output ever appears one animation behind. (Phase 5)

- [ ] **↑↓ move the match strip instead of the shell's history, for any line with something typed on it.** The strip now puts itself up as you type, and it owns the arrows while it is up. At an *empty* prompt there is nothing to match, so no strip and the keys are the shell's — which covers the common "recall the last command" case. What is genuinely lost is recalling history *after* typing a prefix, which PSReadLine does with `HistorySearchBackward`. Our own history is one of the strip's sources, so the same information is reachable a different way; whether that is enough has not been watched. If it is not, the fix is Alt+↑↓ for the strip and ↑↓ back to the shell, not a mode. `src/routes/+page.svelte`, `menuOwns`. (Phase 7 / 12)

- [ ] **`openCompletions` is nearly dead code now.** Tab reaches it only when the strip is closed, which means nothing matched, which means it will usually open nothing. It is still the only path that lists a directory for an *empty* token mid-line. Fold it into the automatic path or delete it once the strip's behaviour has been watched on screen — not before, since it is the fallback that would be missed. `src/routes/+page.svelte`. (Phase 7)

- [ ] **Tab now belongs to VAD/OS, not to the shell.** The suggestion strip intercepts Tab in block mode and completes from a directory listing, so PSReadLine's own completer — which knows commands, parameters, and its own history — never sees the key. The trade is deliberate: that completion happens inside a line editor the block renderer cannot show, so it was invisible here anyway. It is still a real loss for `git chec<Tab>` and for parameter names. Hand Tab back the day the input bar can render what the shell predicts (see the ghost-text idea below, which notes PSReadLine's prediction arrives in the stream for free). `src/routes/+page.svelte`, `src/lib/input.js`. (Phase 7 / 12)

- [ ] **The mirrored selection reads any cell background as "selected".** The input bar shows a selection by scanning the prompt row's cells for a background attribute, which is what makes it work identically for Ctrl+A, Shift+arrow and a mouse selection without knowing one shell's key bindings. A shell that tints a token's *background* for syntax highlighting rather than for selection would read as permanently selected. No tier-1 shell does. Narrow it to the reported selection colour if one ever does. Marked `ponytail:` at the scan. (Phase 12)

- [ ] **Startup is not measured, only improved.** The shell now starts in Rust's `setup` and its output is buffered until the frontend attaches, and the window is created hidden and shown once sized — both aimed at the reported ~0.5s stutter, neither timed. PERFORMANCE.md's measurement protocol should own a cold-start number before any further tuning: the remaining candidates (PowerShell profile load, `font-display: block` on Space Mono, xterm's first fit) are guesses until then. (Phase 7)

- [ ] **A dropped path is quoted from the path's own shape, not from the shell's identity.** A Windows-shaped path gets PowerShell's quoting rules and everything else gets POSIX's, because the PTY does not report which shell is on the other end. Wrong for exactly one case: a POSIX-style shell on Windows (git-bash) handed a `C:\` path. Marked `ponytail:` at `quotePath`; the real fix is the shell registry from [foundation/phase-12-shell-hosting.md](foundation/phase-12-shell-hosting.md), which knows what it spawned. (Phase 12)

- [ ] **Tab-completing a runnable file offers the path, dropping the same file offers the ways to run it.** Two surfaces answering the same question differently, and the drop's answer is the better one — `runOptions` already knows that a `.ps1` is `& path`, a `.sh` is `bash path`, and that a POSIX drop can collapse `chmod +x` into the same selection. The completion menu offers `quotePath(name)` and stops. Unifying them is small (`completions` calls `runOptions` for a file whose extension is in `RUNNERS`), and the reason it is not done yet is that it changes what Enter on a completion means for exactly the files where the user is most likely to have wanted the plain path — completing an argument to another command. Probably wants the run options as *extra* rows below the path rather than instead of it. `src/lib/input.js`. (Phase 7 / 12)

- [ ] **The resize observer now watches `.scroll` as well as the xterm wrapper.** It had to: the cwd panel narrows the scrollport without changing the window, so the wrapper never moves and the PTY was never resized. The observer's callback is not cheap — it re-snapshots the open block, re-shows it, re-runs `settleReveals` and invokes `pty_resize` — and it now fires on anything that changes `.scroll`'s content box, which includes the input bar growing a row. Unmeasured against [docs/PERFORMANCE.md](docs/PERFORMANCE.md)'s budgets. If it shows up, the fix is to compare the observed width against the last one and bail when only the height moved, not to stop observing. The band tween already mutes it for its own duration and calls it once on landing (`bandMoving` / `syncBand`), which is the same idea applied to the one case that provably needed it. (Phase 7)

- [ ] **Markdown renderer — how far does the hand-rolled parser go?** `src/lib/parse.js` now handles six rules: level-2 heading (colon-terminated line with a separate body), list (2+ line body under a level-2 heading), fenced code (2+ consecutive code-shaped lines — shape-based, not language detection: indentation, shell-prompt markers, diff markers, or symbol density), inline code (same shape test per-token: flags, paths, `fn()`, `key=value`), single-line labels (colon with text on the *same* line, e.g. `Usage: run with --foo`), and tone (a warning/error word tints red, success/done tints green). A single-line label only becomes a level-3 heading if it carries a tone — otherwise it's bold prose, specifically so inline code (`--foo`) keeps working on it; a heading's text is never inline-tokenized. A seventh rule marks a **whole command** as one inline code run — a name from a curated `COMMANDS` list, an optional subcommand verb from a curated `SUBCOMMANDS` list, then every argument-shaped token after them, so `git diff --no-index [<options>] <path>` is one span rather than a stray backticked flag inside plain prose. Both lists are curated rather than detected: reading `PATH` would cover every command instead of eighty, at a round trip per render. The subcommand list is a whitelist and was a blacklist first — the set of English words that can follow a tool name is open ("git is not installed", "cmd instead"), the set of verbs tools use for subcommands is not. An eighth rule tints tokens *inside* a code block — flags, `<placeholder>`s, quoted strings — as spans on the code node, colour only (see [decisions.md](decisions.md)); `toMarkdown` ignores them, since a markdown fence carries no inline markup. Emits structured nodes rendered as real DOM, sidestepping the injection question — no markup is ever produced or re-parsed. Open: whether to keep extending this by hand (tables, emphasis, tone beyond headings/labels) or swap to a real renderer once the rule count grows. A real renderer reopens the injection surface and the streaming-reparse cost. Self-check: `node src/lib/parse.check.mjs`. (Phase 3)
- [ ] **Error output as a fenced code block.** Stderr / PowerShell `ErrorRecord` text (`In Zeile:1 Zeichen:1`, `+ CategoryInfo`, `+ FullyQualifiedErrorId`) should render inside a ``` ``` ``` block rather than as prose. Needs the markdown renderer above first, plus a way to tell stderr from stdout — a PTY merges both streams, so the split has to come from either OSC 133 sub-markers or pattern-matching the shell's error format. (Phase 3)
- [ ] **Incremental vs. on-complete markdown rendering** — incremental looks better but re-parsing every chunk is expensive. **Conditionally resolved:** [docs/PERFORMANCE.md](docs/PERFORMANCE.md) now permits incremental parsing under three conditions (parse from the last stable boundary, one parse per frame, raw fallback under flood). It stays open because the boundary logic has to be proven correct against an unterminated fenced code block first; if it cannot be, the answer reverts to on-complete. (Phase 8)

- [ ] **How does a program declare "this output is markdown"?** An OSC private-use marker, an env var the terminal exports so tools can detect it, or both. The marker is cheap and invisible elsewhere; the env var is what gets third-party tools to cooperate without anyone reading a spec. Needs picking before any tool is asked to emit it, because it becomes a compatibility surface the moment one does. (Phase 8)

- [ ] **How much does the shape parser keep doing once a real markdown parser exists?** They solve different problems — one reads *shape* in plain output (`npm`'s `Usage:` is a heading and is not markdown), the other parses actual markdown. Running both means two paths to maintain and two ways to be wrong. Running one means losing either declared-markdown fidelity or the entire plain-output value proposition. (Phase 8)

- [ ] **Do rich embeds count against the scrollback cap by size or by count?** A block with a 4 MB decoded image and a block with four lines of text are one block each. Counting blocks is easy and wrong. (Phase 9)

The same reasoning covers the elevation toggle, which is next-launch on both platforms for a harder reason — a process cannot raise its own token. (Phase 6)

## Known issues

- **A pager's screen is rendered as if it were command output, and it is not.** `git diff` pipes through `less` (git sets `LESS=FRX`, and `-X` means *no alternate screen*), so `syncMode` never fires and the block renderer reads back a buffer that `less` is repainting. What lands in the block is a *screenshot of a pager*, complete with its right-truncation markers (`>` at end of line) and the left-clipped fragments of a previous page. **The parse of that is garbage because the input is garbage** — this is not a renderer bug, and no parser fix improves it. Same root as the `claude` blocker: an interactive program that deliberately avoids the alternate screen. Until the raw-mode trigger is redesigned, `git --no-pager diff` is the workaround, and `PAGER=cat` for the session is the open question below.

- [x] ~~**Three real parser bugs, visible in a diff and independent of the pager.**~~ **All three fixed**, each with a case in `parse.check.mjs`: `diff` joined `COMMANDS` so `diff --git a/x b/x` is one run; a backtick *pair* is now a token whose markers are consumed, so already-marked text is never marked again; and a blank line between two diff lines no longer ends a fence. The third had to be narrowed to diffs after the general form swallowed `npm --help`'s heading and list into one code block — the self-check caught it, which is the entire argument for that fixture existing.

- **`npm ls --all` lands without animating its list.** Reported from [tests.md](tests.md) (2026-08-08): the run bar and the whole-block landing were both right, only the list did not animate. **Most likely not a bug but a cap doing its job and reading like one.** A `<ul class="md-list">` is tier `null` in [reveal-plan.js](../src/lib/reveal-plan.js) — a list is grey prose, so it belongs to the character wave and never gets a bar. The wave then refuses the element outright above `WAVE_MAX_WORDS` (4000 units), returning `null` from `splitChars`, and a full dependency tree is comfortably past that. Above the cap the element is simply unclipped: no wave, and nothing in its place. Confirm that is what happened (a smaller `npm ls` should wave normally — that is the whole test), then decide which way it goes: either a block over the cap is *meant* to land plainly, or it needs the cheap whole-element clip sweep that the over-`LABEL_MAX` path already falls back to for labels. The second is a few lines and keeps the cost O(1) in the block's length. `src/routes/+page.svelte`, `splitChars` / `revealStatic`. (Phase 5)

- **npm 11 blocks esbuild's postinstall.** A fresh clone needs `npm approve-scripts esbuild` or Vite will not run. Worth a note in the README setup steps.
- **Bash tool PATH misses `~/.cargo/bin`** until a terminal restart. Workaround: `export PATH="$PATH:/c/Users/vadim/.cargo/bin"`.
- **Harmless linker warning on every Windows build** — German-language `linker stdout` message about `.dll.lib` / `.dll.exp` creation. Not an error.

## Deferred by design

Rejected or postponed with reasons — see [decisions.md](decisions.md) before reopening.

- Multi-tab / split panes — rejected, a second window covers it.
- Plugin system — rejected, settings are a fixed curated GUI.
- Real Docker containerisation — rejected, "container" means the UI output block.
- SSH / remote sessions.
- ~~Shells beyond bash / zsh / fish / PowerShell.~~ **Reopened.** A terminal that hosts one shell per platform is not a terminal, it is a PowerShell wrapper. Tiered in [shells.md](shells.md), built in [foundation/phase-12-shell-hosting.md](foundation/phase-12-shell-hosting.md).
- Built-in AI client — rejected. VAD/OS renders LLM output; it does not host a model or hold an API key.
- Terminal graphics protocols (Sixel / Kitty / iTerm2) — deferred until a tool in actual use needs one. See [foundation/phase-9-rich-media.md](foundation/phase-9-rich-media.md).
- Config schema migration and versioning — add on the first breaking schema change, not before.
- Full TUI rendering for alt-screen apps — they get the raw xterm fallback, by design.
- Per-orientation startup window sizes. `scaled()` in `src-tauri/src/lib.rs` now uses a single factor for both axes — the smaller of the two screen ratios — after the per-axis version inverted the aspect on a rotated monitor (1080x1920 opened a 596x1102 window instead of ~1060x620). The uniform factor is correct but conservative: on a portrait screen it opens 596x349, short for a 1920px-tall display. Revisit once the product is finished and portrait use is real — a portrait reference size, or remembering the last window geometry, would both cover it.
